# 流形 · Forma 产品与技术设计方案

流形 · Forma 是一款可连接不同 AI 的独立回答面板。用户提出问题后，中央液态粒子聚合为文字、图表、示意动画或媒体内容；追问可以直接修改当前画面，同时保留历史版本。

首版确定采用独立面板，先做桌面浏览器体验，再考虑桌面封装和聊天软件插件。产品的核心是持续、可交互的回答画布。粒子提供统一的视觉材料和变化语言，内容成形后保持清晰、可复制、可核对。

本方案为 2026 年 10 月 9 日的设计基线。附带交互原型使用预设内容，演示液态待机、文字、图表和轨道动画；尚未连接 AI，也未实现真实视频生成。下文的性能数字、阶段工期和质量门槛均为拟定目标，需在开发中验证。

## 产品定位与首批使用场景

产品已定名：中文名「流形」，英文名「Forma」，统一展示为「流形 · Forma」。品牌文案：让思想，自然成形。核心承诺是：让回答以适合内容的形态出现，并且能够在同一块画布上继续讨论和修改。

首批面向经常用 AI 理解概念、比较数据、推演方案和进行创意沟通的人。优先选择能够验证表达价值的三个场景：

| 场景 | 用户提问 | 画布的表达 | 下一步交互 |
| --- | --- | --- | --- |
| 理解过程 | 月球怎样绕地球运动 | 粒子聚成天体和轨道，清晰标注示意与比例限制 | 播放、暂停、拖动位置，再追问 |
| 理解数据 | 这四个月的数据有什么变化 | 显示来源、单位、可读数的图表和一句结论 | 切换图形、选择月份、对选中数据提问 |
| 修改方案 | 把这三个方案比较一下 | 可选择的比较结构，优势和限制有文字依据 | 固定两个方案，只修改第三个 |

普通事实问答、长文阅读和代码仍应优先使用清晰文字。用户选择“自动表达”时，由内容类型和设备能力共同决定形态；用户可随时切换到文字视图。视觉形式不能遮盖信息缺失。

产品价值需要用理解速度、任务完成率、修改成本和重复使用验证。初次观看时觉得漂亮，是体验反馈的一部分，不能独自证明长期价值。

## 独立面板的界面结构

桌面默认采用一个主画布、一个底部输入区和按需展开的历史栏。首次进入时，中央有一团低速流动的液态粒子，四周留白；不展示没有内容的卡片和仪表盘。

顶部保留产品名、当前会话名、当前模型及连接状态。模型配置收进设置；切换模型时，说明下一次提问会把哪些会话内容发送给新提供方。正常使用不展示粒子数量、协议版本或渲染后端。

画布占据主要空间。内容按语义自然排布，相关对象保持邻近；复杂回答可分成若干连续段落或场景。长文正常纵向阅读，不能把一整篇文章缩小塞进单屏。移动端把比较区域堆叠，保留相同的数据与对象身份。

底部输入区支持输入、停止和针对选中对象提问。首版增加“自动／文字／图表／演示”的表达偏好，默认自动。媒体生成需要成本或更长等待时，显示具体任务和费用上限后由用户启动。

历史栏保存问题与场景缩略图，默认折叠。选择过去回答时先查看静态快照，再按需恢复交互。浏览历史不重新请求模型。

画布级常用操作为返回上一版本、复制回答、查看来源和导出。对象级操作在选中后出现，例如查看数据、解释这部分、固定内容。键盘与触摸用户可以通过对象列表访问这些操作。

## 液态粒子与视觉规则

粒子的视觉身份采用柔和的流动边界、局部黏连、少量高光和细颗粒。整体是安静、具有生命感的材料。默认浅色或深色随系统变化，正文以中性色为主，强调色集中在当前对象和图形标记上。默认无声音。

粒子在不同阶段的行为具有明确含义：

| 阶段 | 可见行为 | 内容和操作 |
| --- | --- | --- |
| 待机 | 中央低速流动，长时间无操作后趋于静止 | 输入可立即使用 |
| 请求已发送 | 粒子轻微收拢 | 显示真实任务状态，可停止 |
| 内容逐步到达 | 完整内容块逐块成形，保留稳定区域 | 已完成部分可阅读 |
| 成形 | 粒子移动到文字或图形的轮廓与区域 | 转场可跳过 |
| 稳定阅读 | 正文、标注和控件完全清晰，装饰运动停止 | 可复制、选择、操作 |
| 局部修改 | 受影响区域解聚并重新组织 | 未变化部分保持原位 |
| 工具或媒体等待 | 已有内容保留，任务区域显示真实状态 | 可取消，不虚构进度百分比 |
| 错误或停止 | 保留最后一个有效版本 | 给出文字说明与重试入口 |

首次完整成形目标约为 600–1000 毫秒，局部更新约为 180–350 毫秒。已有内容在等待新结果时保持可见。用户应能跳过动画；减少动态效果模式直接呈现内容，过程动画由用户主动播放。

不能用文字持续抖动、数字闪烁或反复消散表现“智能”。粒子快慢也不代表模型置信度、思考深度或实际进度。

同一数据点、文字块和图形对象具有稳定 ID。对象更换位置时，尽量由原有粒子移动过去；数量变化时使用粒子池复用。跨场景不强求逐个粒子永久对应，优先保持用户能识别的对象连续性。

目标定位完成后，显示引擎把视觉内容交接给清晰的文字、矢量图、控件或媒体层。用户看到统一画面，同时保留文字选择、屏幕阅读、精确命中和原始数据。

## 用户交互与跨轮连续性

一次提问会生成一个回答场景。每次已提交的修改产生新版本，记录提出修改的用户事件、受影响对象、数据版本和模型来源。

追问分为三类。改变图表类型、拖动时间、展开已有细节属于本地交互，立即执行，不消耗模型请求。解释选中对象、比较另一种假设属于语义追问，发送相关对象和必要上下文。生成新图片或视频属于工具任务，有独立状态、取消和结果回填。

用户点选一个图表区域后说“解释这里”，请求中携带对象 ID、数据切片和当前版本。不能只依赖截图让模型重新猜测。用户固定的内容在后续修改中保留；需要改变时明确指出冲突。

用户正在阅读、拖动、选择文字或输入时，新内容不能抢走焦点、覆盖输入或自动滚到另一区域。对正在操作对象的更新先暂存，操作结束后应用或提示存在新版本。

连续修改只提交与当前版本匹配的结果。旧请求迟到时不覆盖新回答。用户停止生成后，已提交内容保留，未提交草稿丢弃。重试创建新请求并复用有效上下文。

返回上一版本恢复已保存的场景与交互状态，不会撤销已经发生的外部任务。重放只重现视觉过程，不重新调用模型、下载资源或生成媒体。

## 三个完整使用流程

**数据比较。** 用户粘贴四个月的数字。面板先识别字段和单位；不明确时保留原表并询问含义。确认后，粒子聚成图表，来源显示为“本次用户输入”。用户选择“换成折线”，本地改变形状，数字保持不变。用户点选四月并追问“为什么上升”，系统检查现有材料能否支持原因；缺少依据时明确区分观察与推测。

**动态解释。** 用户问月球怎样运动。面板生成带文字说明的轨道示意，标明不是比例模型。用户按播放，拖动位置观察变化；角度和播放状态由本地场景状态控制。继续问“为什么不是每个月都有月食”，模型只更新解释所需的图形和文字，并说明示意范围。动画的物理关系来自受审核的模板或经验证的计算模块。

**创意短片。** 用户要求一个十秒产品概念片。面板先形成可编辑分镜，用户确认具体生成任务及成本后，才调用视频服务。等待期间保留分镜和真实任务状态。完成后回填可播放视频，默认静音，具有播放、暂停、进度和字幕能力。用户修改一个镜头时，仅重新生成对应素材；取消后是否停止计费以服务方实际状态为准。

原型已经演示前两个流程中的视觉和本地交互片段。以上真实模型理解、来源核验、轨道知识解释以及视频任务链仍属于后续实现范围。

## 像素适配与渲染架构

屏幕像素决定可呈现的细节上限，粒子数还需要受实际画布面积和设备性能约束。3840 × 2160 的显示区域有 8,294,400 个物理像素，不宜默认创建同样数量的独立粒子。

使用面板当前可见面积计算预算，而非读取整块显示器分辨率。拟定公式如下，参数用于性能测试起点：

```text
effectiveDpr = min(devicePixelRatio, qualityDprCap)
effectiveArea = visibleWidthCss × visibleHeightCss × effectiveDpr²
requestedParticles = round(effectiveArea / sampleSpacing²)
particleCount = min(requestedParticles, deviceBudget, rendererBudget)
```

例如 800 × 520 CSS 像素、有效 DPR 1.5、采样间距 6，对应约 26,000 个候选粒子，再由性能预算限制。缩小窗口不会把内容变小到不可读，而是重新排布内容、减少装饰粒子。跨显示器和浏览器缩放后重新计算预算。

显示引擎分成四层：

| 层 | 职责 | 建议实现 |
| --- | --- | --- |
| 场景与布局 | 对象、数据、语义顺序、响应式位置 | TypeScript 场景模型和布局模块 |
| 粒子与转场 | 采样、目标分配、流场、聚合与消散 | 首个正式版本 WebGL2，统一 renderer 接口 |
| 清晰内容 | 可选择文字、图表标签、表格和控件 | DOM 与 SVG，共享布局结果 |
| 媒体与事件 | 图像、视频、命中测试、焦点和输入 | 浏览器媒体元素及受控事件路由 |

当前交互原型用 Canvas 2D 验证观感，不用于证明正式粒子规模或帧率。正式版本保留 Canvas 2D 低粒子后备；WebGL2 不可用时继续显示文字、SVG 和媒体。WebGPU 后续作为高性能后端，依据实际能力检测启用。WebGL2 与 WebGPU 都有独立的图形 API，不能假设无需适配就可互换。[WebGL2 官方规范](https://registry.khronos.org/webgl/specs/latest/2.0/)，[WebGPU 官方介绍](https://developer.chrome.com/docs/web-platform/webgpu/overview)

性能策略先降低粒子数、分辨率、光晕和更新频率，最后取消装饰运动；保留内容清晰度。使用连续帧时间监测和恢复迟滞，避免画质反复跳变。页面不可见、画布离开视口或内容稳定后停止不必要的绘制。

起始预算建议为低档约 2,000–6,000、中档约 12,000–30,000、高档不超过 60,000 个粒子，均需实测。设备档位来自短时本地测量，不以昂贵硬件型号作为先决条件。记录测试中的分辨率、DPR、粒子数和后端，帧率数据才有可比性。

## AI 输出契约与流式协议

模型输出的是内容、数据关系、布局意图和允许的交互。渲染引擎负责具体像素与每一帧运动，模型不逐像素输出坐标，也不逐帧生成 UI 代码。

内部格式暂称 Panel Scene 0.1，是本产品的协议草案。正式开发时需要补齐 JSON Schema、版本迁移和符合性测试；本方案不宣称它已经成为公共标准。

一个场景包含 sceneId、revision、semanticSummary、nodes、datasets、assets、actions 和 provenance。节点使用稳定 ID，首版只允许 text、group、chart、table、diagram、timeline、image、video、control 等注册类型。布局使用堆叠、网格、对齐和最小尺寸等约束，避免模型输出整页绝对像素坐标。

图表和表格必须引用同一份类型化数据。数据标记单位、字段类型、空值和来源；不得把缺失值自动变成零。事实结论与数据或来源关联，来源显示是可核对入口，并不自动证明内容真实。

下面是最小场景结构示意：

```json
{
  "protocol": "panel-scene/0.1",
  "sceneId": "monthly-usage",
  "revision": 1,
  "semanticSummary": "四个月的使用次数为32、58、45、76次。",
  "datasets": {
    "usage": {
      "columns": [
        {"id": "month", "type": "string"},
        {"id": "count", "type": "number", "unit": "次"}
      ],
      "rows": [
        {"month": "1月", "count": 32},
        {"month": "2月", "count": 58},
        {"month": "3月", "count": 45},
        {"month": "4月", "count": 76}
      ],
      "source": {"kind": "demo", "label": "示例数据"}
    }
  },
  "nodes": [
    {
      "id": "usage-chart",
      "type": "chart",
      "props": {
        "kind": "bar",
        "dataset": "usage",
        "x": "month",
        "y": "count",
        "title": "月使用次数"
      },
      "a11yLabel": "四个月使用次数比较"
    }
  ],
  "actions": [
    {
      "id": "show-line",
      "target": "usage-chart",
      "execution": "local",
      "operation": "setChartKind",
      "args": {"kind": "line"}
    }
  ]
}
```

传输事件共有 request.started、scene.begin、node.upsert、data.upsert、asset.status、scene.commit、request.completed、request.failed 和 request.cancelled。每条事件带 requestId、sceneId、sequence、eventId；一次事务带 transactionId、baseRevision 和 nextRevision。

完整 JSON 对象到达后才校验；不把尚未闭合的流式 JSON 当作可执行场景。通过模式、引用、配额与操作校验的草稿写入暂存区。一次 scene.commit 原子更新一组相关节点与数据，避免数值已变而标签仍旧。长回答可以分多个小事务逐步提交。

重复 eventId 幂等丢弃；顺序缺失时请求补齐或场景快照；baseRevision 不匹配时拒绝覆盖。校验失败允许一次有界修复，再失败就保留文字回答和最后有效画面。只发布有效的已提交状态，错误日志不灌入用户画布。

用户事件回传 interactionId、sceneId、revision、nodeId、eventType、value 和必要的选择上下文。任意脚本、eval、模型生成的网络地址执行指令不属于该契约。

## 多模型接入与插件路线

独立面板具有自己的会话、场景状态和显示引擎。模型提供方只是回答生成服务。更换模型时，场景数据与交互历史仍留在面板中。

适配器提供统一的能力说明、流式回答、取消和可选工具调用接口。能力协商包含结构化输出、工具调用、图像输入、上下文限制，以及可用的媒体工具。服务方不支持的能力应隐藏或降级，不伪造兼容。

接入分为三个等级：

| 等级 | 模型条件 | 面板行为 |
| --- | --- | --- |
| 完整结构化接入 | 稳定产生约束 JSON 或工具调用 | 直接生成场景与局部修改 |
| 受限接入 | 能遵循 JSON 指令但保证较弱 | 严格校验，一次修复，失败保留文本 |
| 文本接入 | 只能稳定提供文字 | 显示清晰文字；仅从明确结构提取列表或表格，不猜造图表 |

首版以两家独立提供方的真实端到端接入验收多模型能力，具体模型和 API 版本在实施时核验。浏览器前端不保存长期 API 密钥；首版个人本机体验由仅监听本机的服务端网关持有凭据。API 兼容服务可以共用传输层，但不能因此假设所有功能完全兼容。

A2UI 已提供声明式 JSON、受信任组件目录和可增量更新的 UI 表达方式。建议评估采用其基础结构或提供映射适配，把粒子转场和连续画布保留为本产品渲染层能力；不把一整套组件协议从头重复设计成生态壁垒。[A2UI 官方项目](https://github.com/a2ui-project/a2ui)

MCP Apps 适合后续把面板作为交互界面嵌入支持它的聊天宿主。它处理 UI 资源、宿主通信和沙箱等问题，宿主支持情况因客户端而异。它不自动解决模型接入，也不能保证一个插件替换所有 AI 软件的原生回复框。[MCP Apps 官方说明](https://modelcontextprotocol.io/docs/extensions/apps)

路线为独立面板 SDK、模型适配器、嵌入组件、指定宿主插件。网站注入或浏览器扩展作为后续逐站点适配选项，不放进首版验收。

## 应用架构与模块边界

首版建议使用 TypeScript、React 与 Vite 构建前端，Node.js 本地网关负责模型连接。前端保存可恢复的场景快照和操作日志，服务端只保存必要配置及任务状态。依赖版本在开始实现时锁定。

| 模块 | 输入与输出 | 主要责任 |
| --- | --- | --- |
| Provider Adapter | 提问和能力描述 → 统一事件流 | 鉴权、流式传输、取消、错误归一 |
| Answer Planner | 需求与上下文 → 表达意图 | 选择适合的内容形态和模板 |
| Scene Validator | 候选场景 → 合法事务或错误 | 类型、引用、来源字段和资源限制 |
| Scene Store | 合法事务 → 可恢复版本 | 原子提交、历史、选择和撤销 |
| Layout Engine | 场景与容器尺寸 → 稳定布局 | 响应式排布与阅读顺序 |
| Renderer | 布局与转场 → 清晰画面 | 粒子、DOM、SVG、媒体合成 |
| Event Router | 用户事件 → 本地操作或语义追问 | 保留对象上下文与权限边界 |
| Media Jobs | 分镜或素材请求 → 异步任务结果 | 预算、状态、取消、素材复用 |

建议的代码组织为 apps/panel、apps/gateway、packages/protocol、packages/scene-store、packages/renderer、packages/adapters、packages/components、packages/media 和 fixtures。原型验证结束后再初始化正式工程，避免把演示脚本直接当作生产架构。

回答规划可以是一次模型调用的一部分，首版不默认使用另一个模型重写所有回复。组件和模板目录由应用维护。布局、形变、数据筛选、播放和撤销在本地处理，减少等待与模型成本。

场景保存语义数据、布局约束、素材引用和稳定随机种子，不保存每一帧像素。静态导出优先采用文字、SVG、PNG 和数据表；可交互导出后续通过可移植场景包实现。

## 动画与短视频的边界

面板内的动画包含两类能力。第一类是引擎实时渲染的变化，例如轨道、流程、几何变换和参数推演，可以直接拖动与修改。第二类是图片或视频服务生成的媒体素材，需要单独的生成工具、等待与成本。

首版支持受控的二维过程动画和已有视频播放。下一阶段加入分镜编辑与一个视频工具适配器。视频生成默认不绑定每次普通回答，不把背景粒子运动当作已经生成了一段视频。

媒体节点包含 jobId、state、poster、assetRef、duration、captions、source 和 error。状态至少有 queued、running、completed、failed、cancel_requested、cancelled。只有服务端确认结果就绪，才显示可播放状态；取消请求与取消成功要分别呈现。

生成任务用幂等键避免重试重复扣费。素材按版本与生成参数缓存。流失连接后可以恢复查询任务状态。用户可导出已有素材；将实时场景录制成视频属于另一条导出流程，需要处理字体、帧率、音频、编码和跨域素材，放入后续范围。

## 可用性与数据边界

所有回答同时保存文字摘要和语义结构。文字可以选中复制；图表可以查看原始数据；动画具有文字说明、播放控制和逐步查看方式；视频保留字幕或转写入口。减少动态效果随系统偏好生效，也允许用户在产品中选择。

颜色不能是区分含义的唯一方式。图表包含轴、单位、标签和适当的对比度。键盘焦点、触摸命中区域与阅读顺序来自真实元素，不依赖粒子位置。

模型输出只引用允许的组件、动作和素材类型。插件组件必须经过应用注册，且在需要时使用隔离容器。外部写入操作不能藏在自动播放或图形点击的副作用里。

本地网关保持凭据在服务端，校验来源与会话授权，避免把开发服务裸露到局域网。素材加载经过类型、体积和来源校验；不让模型任意请求本机地址或执行代码。场景配额限制节点数、数据规模、动画时长和资源占用。

切换提供方、上传附件或使用媒体工具时，只发送当前任务必需的内容。默认不上传设备原始性能数据，不把完整历史交给每一个新模型。用户可以查看发送范围、删除本地会话及导出数据。

这些约束由应用代码执行。提示词负责说明格式，不能承担权限控制。

## 首版范围与后续阶段

首版目标是完成一次可靠的闭环：提问 → 有效内容逐步成形 → 本地交互 → 针对对象追问 → 保留历史 → 失败可恢复。

| 阶段 | 交付 | 进入下一阶段的条件 |
| --- | --- | --- |
| 体验原型 | 液态、文字、图表、动画及状态返回 | 用户确认视觉方向和变化方式 |
| 核心工程 | 协议、校验器、版本状态、双层渲染、响应式 | 固定场景可重放，错误数据不破坏画面 |
| 真实 AI 首版 | 两个模型适配器，流式生成和对象追问 | 同一评测集通过两家提供方 |
| 媒体扩展 | 分镜、素材缓存、异步视频任务 | 任务恢复、取消和成本提示可验证 |
| 嵌入生态 | SDK、场景包与一个宿主插件 | 宿主能力协商和状态回传通过测试 |

正式 MVP 包含文字、列表、表格、柱状图、折线图、简单流程／轨道示意、图片和已有视频播放，支持一次回答中的适量组合。复杂三维场景、任意 HTML 应用、插件市场、团队协同、全部 AI 宿主注入和自动生成所有视频不列入首版。

按一名具备前端与图形经验的开发者持续投入，固定场景核心约需 1–2 周，模型接入和状态完整性约需 1–2 周，适配、性能与用户试用约需 1–2 周。合计 3–6 周是规划区间，依赖实际设备表现、模型格式稳定性与需求变更，不是交付承诺；视频服务和宿主插件另算。

现在最合适的开发顺序是：先用三组固定场景把画面做对，再让模型填入同一份结构，最后开放更多场景。

## 验收标准与评估方法

以下是开发验收目标，不是本次原型的实测性能结果。

| 维度 | 拟定门槛 | 测量方法 |
| --- | --- | --- |
| 本地交互 | 控件反馈 P95 不超过 100 毫秒 | 输入事件到可见反馈，排除模型网络等待 |
| 转场性能 | 中档桌面目标 60 fps；降级档目标 30 fps | 记录设备、视口、DPR、粒子数与帧时间分位数 |
| 流式呈现 | 有效事务到达后 P95 200 毫秒内可见 | 服务端到达时刻与提交渲染时刻分开记录 |
| 内容精度 | 图表与原始数据完全一致 | 测试空值、负值、长标签、单位和极端数值 |
| 版本可靠性 | 乱序、重复、旧请求结果不会覆盖新状态 | 故障注入与可重放事件集 |
| 可访问性 | 所有核心操作可用键盘完成；关闭动效仍可理解回答 | 焦点检查、读屏抽查、320 像素窄屏 |
| 模型适配 | 两家提供方各跑至少 50 个固定任务；有界修复后结构有效率目标 95% | 记录原始成功率、修复率和文字回退率 |
| 恢复能力 | 中断、刷新和资源失败后保留最后有效场景 | 断网、取消、浏览器刷新和任务重连 |
| 用户收益 | 首轮 8–12 人探索试用，比较理解正确率、耗时与修改成功率 | 相同内容交叉比较文字版与画布版 |

模型生成耗时、视频排队耗时和用户网络条件单独统计，不能算成渲染引擎性能。结构合法不等于答案正确，需要内容评估与数据一致性检查。

首版性能设备建议包含当前 Mac、一台普通 Windows 设备及至少一台移动设备。具体硬件和浏览器版本在测试时登记；尚未测试的平台不列为已经兼容。

如果用户在简单问题上觉得动画拖慢阅读，默认降低动效；如果图表的理解收益不明显，优先修正信息结构。通过任务表现决定哪些视觉形式成为默认。

## 成本与后续产品路线

每次回答的主要可变成本来自模型输入输出、外部工具和生成媒体。粒子运动与图表本地交互不应产生模型费用。避免每次样式切换重新调用模型；对已核验的场景、摘要和素材复用缓存。

成本记录区分服务端估算与账单实际值。视频等高成本工具独立配置额度，不把文字回答的预算默认扩展到媒体生成。

个人产品可以先提供本地配置模型的模式，以核心显示体验积累使用反馈。后续商业方向包括付费桌面体验、托管模型服务及面向其他产品的渲染 SDK。早期优先验证用户是否持续使用、是否愿意为更低的理解和修改成本付费，暂不确定定价。

开放策略建议公开场景格式、适配器接口和基础示例，保留高质量动效、复杂表达组件、可视化编辑和托管能力作为可持续投入的部分。真正需要积累的是可靠的表达组件、连续修改体验、跨设备性能和评测数据。
